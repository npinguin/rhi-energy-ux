# Release Governance

RHI Energy UX follows `docs/UX_RELEASE_STANDARD.md`. This file adds Energy-specific implementation rules.

## Canonical owners

| Concern | Owner |
| --- | --- |
| Package version | `package.json` |
| Energy release context | `release/product.json` |
| Runtime version | generated by `source/build-energy-bundle.py` from `package.json` |
| Compatibility/publication metadata | synchronized from the owners above |
| Test ownership | `validation/OWNERSHIP.json` |
| Runtime qualification | `release/QUALIFICATION.json` |
| Published candidate | immutable GitHub tag/release |

The literal UX version in canonical source is a build input/template, not a release authority. The generated HACS bundle always receives the version from `package.json`.

## Release path

```text
branch
→ PR
→ one full Validate gate
   → candidate build
   → owned test suites
   → deterministic second-build proof
   → committed-dist equality
   → HACS validation
→ squash merge
→ Publish HACS verifies exact committed artifact
→ immutable HACS-visible TEST CANDIDATE
→ target HA qualification + rollback
→ manual stable promotion of exact immutable candidate
```

**Candidate publication does not rebuild. Stable promotion does not rebuild.**

## Test ownership

Testing follows the same ownership model as runtime code.

Normative sources:

- `docs/TEST_GOVERNANCE.md`
- `validation/OWNERSHIP.json`
- `validation/validate_test_ownership.py`

Rules:

1. one invariant has one test owner;
2. domain tests do not assert package/release identity;
3. footer tests do not assert branding delivery;
4. branding tests do not own header geometry;
5. behavior is preferred over incidental implementation details;
6. when several owners fail for one local change, investigate ownership drift before changing every test.

## Release identity

Run `npm run release:sync` when preparing a new candidate. It synchronizes machine-readable compatibility/status identity from:

- `package.json`;
- `release/product.json`.

Release notes and changelog remain required human history, not machine runtime authorities.

## Published-version immutability

Published runtime bytes are immutable.

For a PR using an already published package version, Validate builds the branch and compares the generated runtime JS and runtime assets with the published tag:

- identical runtime bytes → governance/test/documentation refactoring is allowed without fake version churn;
- changed runtime bytes/assets → the next package version is mandatory.

Build metadata may evolve with governance/source traceability, but published runtime payload never moves.

## Build budget

Normal candidate: **2 builds total**.

- build 1: complete PR validation;
- build 2: deterministic reproducibility proof.

Main publication: **0 builds**.
Stable promotion: **0 builds**.

Any extra build is exceptional, not standard procedure.

## Energy boundaries

UX owns presentation only. Energy semantics come from the canonical public Energy contracts through the registry/gateway/model chain.

Backend release identity comes only from `sensor.energy_release_contract.backend_release`; UX never maps or guesses it.

## Qualification

Static CI is not target Home Assistant evidence. `release/QUALIFICATION.json` binds runtime and rollback proof to the exact immutable candidate tag/SHA.

Rollback remains a previous immutable HACS version.
