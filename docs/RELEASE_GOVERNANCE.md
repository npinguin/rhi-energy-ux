# Release Governance

RHI Energy UX follows `docs/UX_RELEASE_STANDARD.md`. This file adds Energy-specific implementation rules.

## Canonical owners

| Concern | Owner |
| --- | --- |
| Package version | `package.json` |
| Energy release context | `release/product.json` |
| Runtime version | generated by `tools/build.py` from `package.json` |
| Source ownership/build order | `src/OWNERSHIP.json` + `src/manifest.json` |
| Compatibility/publication metadata | synchronized from canonical release owners |
| Test ownership | `validation/OWNERSHIP.json` |
| HACS package | generated `dist/` + `dist/PACKAGE_MANIFEST.json` |
| Runtime qualification | `release/QUALIFICATION.json` |
| Published candidate | immutable GitHub tag/release |

Do not duplicate current package/backend identity in engineer notes or validators as an independent authority.

## Release path

```text
branch
→ generate complete candidate package
→ PR
→ one full Validate gate
   → candidate build
   → owned test suites
   → complete-package immutability check
   → deterministic second-build proof
   → committed-dist equality
   → HACS validation
→ squash merge
→ Publish HACS verifies complete committed dist package
→ create or verify immutable tag
→ normal GitHub Release contains notes only and zero assets
→ immutable HACS-visible TEST CANDIDATE
→ target HA qualification + rollback
→ manual stable promotion of exact immutable candidate
```

Candidate publication does not rebuild. Stable promotion does not rebuild.

## Test ownership

Normative sources:

- `docs/TEST_GOVERNANCE.md`
- `validation/OWNERSHIP.json`
- `validation/validate_test_ownership.py`

One invariant has one owner. Domain tests do not own release identity. Footer tests do not own branding delivery. Branding tests do not own layout geometry.

## Release identity

Run `npm run release:sync` when preparing a new candidate. It synchronizes machine-readable release metadata from `package.json` and `release/product.json`.

Release notes and changelog are human history, not machine authorities.

## Published-version immutability

Published HACS package bytes are immutable.

For an already published version, Validate rebuilds and compares the **complete generated `dist/` tree** with the immutable tag:

- identical package bytes → governance/test/documentation refactoring may continue without fake version churn;
- any changed runtime, asset, checksum or package-manifest byte → a new package version is mandatory.

## Build budget

Normal candidate: **2 builds total**.

- build 1: complete PR validation;
- build 2: deterministic reproducibility proof.

Main publication: **0 builds**.
Stable promotion: **0 builds**.

## HACS nested-asset delivery

Energy contains nested package assets. Tagged HACS plugin releases therefore contain **zero GitHub Release assets**. Current HACS prefers any tagged release assets as the install payload, so even checksum or qualification attachments can suppress installation of the immutable `dist/` subtree.

The immutable tag owns the installable `dist/` subtree. The GitHub Release carries notes/version visibility only.

Publication is idempotent: an existing tag/release is accepted only if its complete `dist/` package matches the current candidate byte-for-byte and the release targets that immutable tag. It is then verified without mutation.

## Energy boundaries

UX owns presentation only. Energy semantics come from canonical public Energy contracts through registry/gateway/model boundaries.

Backend release identity comes only from `sensor.energy_release_contract.backend_release`; UX never maps or guesses it.

## Qualification

Static CI is not target Home Assistant evidence. `release/QUALIFICATION.json` binds runtime and rollback proof to the exact immutable candidate tag/SHA.

Rollback is a previous immutable HACS version.
